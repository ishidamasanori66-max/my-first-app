# プラチナカリキュラム：技術選定とメリット総括

## 概要

本ドキュメントは、中小企業向けAI伴走型開発教育「プラチナカリキュラム」における技術選定の根拠と、各視点からのメリットをまとめたものです。

---

## カリキュラム全体における位置づけ

| ステージ | 技術スタック | ゴール |
|---|---|---|
| ブロンズ | Python + Pandas + Google Colab | データ操縦術、Excel業務の自動化 |
| シルバー | React (Vite) + Supabase + Codespaces + Claude Code | 現場の業務アプリを自作 |
| ゴールド | + Edge Functions + 外部API連携 | バラバラなシステムを繋ぐ |
| **プラチナ** | **Python + LangChain + Claude API + ベクトルDB** | **AI社員による自律化** |

---

## プラチナの目標

```
「AI社員」の導入

・人間の指示を待たずにAIが判断・実行
・定型業務の完全自動化
・問い合わせへの自律的な対応
・データ分析から提案まで自動化
```

### 従来のAI vs AIエージェント

```
【従来のAI（チャットボット）】
人間: 「明日の予定を教えて」
AI: 「カレンダーを確認してください」（情報を返すだけ）

【AIエージェント】
人間: 「明日の会議を調整して」
AI:
  1. カレンダーを確認（ツール実行）
  2. 参加者の空き時間を照合（ツール実行）
  3. 最適な時間を提案
  4. 承認されたら予定を登録（ツール実行）

→ AIが自ら「考えて」「行動する」
```

## LangChain とは

### 概要

```
LLM（大規模言語モデル）を使ったアプリ開発のフレームワーク

・複数のLLMを統一的に扱える
・ツール連携（API呼び出し、DB操作等）
・メモリ管理（会話履歴の保持）
・RAG（社内文書を参照した回答）
```

### 競合・代替ツール

| ツール | 特徴 | 評価 |
|---|---|---|
| **LangChain** | Python、最も普及、情報豊富 | ◎ 採用 |
| LlamaIndex | RAG特化、検索に強い | ○ 参考 |
| Dify | ノーコード寄り、GUI操作 | △ |
| Flowise | ノーコード、LangChainベース | △ |
| CrewAI | マルチエージェント特化 | ○ 発展で紹介 |

### LangChain を選ぶ理由

```
1. 最も普及している
   → 情報・サンプル・コミュニティが豊富

2. Pythonベース
   → ブロンズで習得済みの言語を活用

3. LLM非依存
   → Claude, OpenAI, Gemini 等を切り替え可能

4. 包括的な機能
   → エージェント、RAG、ツール連携すべて対応
```

## Claude API を主軸とする理由

### LLM の選択肢

| LLM | 提供元 | 特徴 |
|---|---|---|
| GPT-4o / GPT-4 | OpenAI | 定番、情報最多 |
| **Claude 3.5/4** | **Anthropic** | **長文理解◎、コード生成◎** |
| Gemini | Google | Google連携、マルチモーダル |
| Command R+ | Cohere | RAG特化 |
| Llama 3 | Meta | オープンソース、ローカル実行可 |

### Claude vs OpenAI 比較

| 観点 | OpenAI (GPT-4o) | Claude (3.5 Sonnet) |
|---|---|---|
| 情報・サンプル量 | ◎ 最多 | ○ 増加中 |
| コード生成 | ◎ | ◎ |
| 長文理解 | ○ 128K | ◎ 200K |
| 料金 | 中程度 | やや安い |
| 日本語 | ○ | ◎ |
| ツール利用 | ◎ Function Calling | ◎ Tool Use |

### Claude を選ぶ理由

```
1. カリキュラムの一貫性
   シルバー・ゴールド: Claude Code を使用
   プラチナ: Claude API を使用
   → 受講者が Claude に慣れている

2. 長文コンテキスト
   RAG（社内文書検索）で大量の文書を扱う
   → Claude の 200K コンテキストが有利

3. 日本語能力
   中小企業の業務 = 日本語中心
   → Claude の日本語は高品質

4. ツール利用能力
   AIエージェント = ツールを使う
   → Claude の Tool Use は高性能
```

### LangChain での LLM 切り替え

```python
# Claude を使用
from langchain_anthropic import ChatAnthropic
llm = ChatAnthropic(model="claude-sonnet-4-20250514")

# OpenAI に切り替える場合
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o")

# 以降のコードは同じ
# → 特定のLLMに依存しないスキルが身につく
```

## ベクトルDB とは

### 用途

```
社内文書・マニュアル・過去の対応履歴などを
AIが検索・参照できるようにする
```

### 仕組み（RAG: Retrieval-Augmented Generation）

```
【登録フェーズ】
社内文書 → 埋め込み（Embedding） → ベクトルDBに保存

【検索フェーズ】
質問 → 埋め込み → 類似ベクトル検索 → 関連文書を取得

【回答フェーズ】
関連文書 + 質問 → LLM → 文書に基づいた正確な回答
```

### 主要なベクトルDB

| DB | 特徴 | 評価 |
|---|---|---|
| **Supabase pgvector** | PostgreSQL拡張、既存構成に追加可能 | ◎ 採用 |
| Pinecone | マネージド、スケーラブル | ○ |
| Chroma | オープンソース、軽量 | ○ |
| Weaviate | オープンソース、高機能 | ○ |

### Supabase pgvector を選ぶ理由

```
1. 既存構成との統合
   シルバー・ゴールドで Supabase を使用済み
   → 新しいサービスを追加する必要がない

2. コスト効率
   既存の Supabase プランで利用可能
   → 追加コストが最小

3. 学習済みの知識を活用
   PostgreSQL の操作方法は習得済み
   → pgvector 拡張を追加するだけ

4. 一元管理
   アプリデータとベクトルデータを同じDBで管理
   → 運用がシンプル
```

## 中小企業での活用例

### 1. 社内問い合わせ対応AI

```
【従来】
社員: 「有給の申請方法は？」
総務: マニュアルを探して回答（5分）

【プラチナ】
社員: 「有給の申請方法は？」
AI: 社内マニュアルを検索 → 手順を回答（5秒）

【効果】
・総務の問い合わせ対応時間を90%削減
・24時間対応可能
・回答品質の均一化
```

### 2. 顧客対応の自動化

```
【従来】
顧客: 「注文状況を教えて」
担当者: システムを確認して返信（10分）

【プラチナ】
顧客: 「注文状況を教えて」
AI:
  1. 顧客を特定（DBツール）
  2. 注文履歴を検索（DBツール）
  3. 配送状況を確認（APIツール）
  4. 状況を整形して返信（自動・即時）

【効果】
・即時対応による顧客満足度向上
・担当者の負担軽減
・営業時間外も対応可能
```

### 3. 在庫発注の自動化

```
【従来】
担当者: 毎日在庫を確認 → 発注判断 → 発注処理

【プラチナ】
AI:
  1. 在庫データを定期監視
  2. 閾値を下回ったら発注判断
  3. 過去の発注パターンを分析
  4. 発注書を自動作成
  5. 担当者に承認依頼を通知
  6. 承認後、発注APIを実行

【効果】
・発注漏れの防止
・適正在庫の維持
・担当者は承認のみで完了
```

### 4. レポート・分析の自動化

```
【従来】
経営者: 「先月の売上分析して」
担当者: データ集計 → 分析 → レポート作成（数時間）

【プラチナ】
経営者: 「先月の売上分析して」
AI:
  1. DBからデータ取得（ツール）
  2. 統計分析を実行（ツール）
  3. グラフを生成（ツール）
  4. レポートを作成
  5. 改善提案まで出力（数分）

【効果】
・分析のスピード向上
・定期レポートの自動化
・データに基づいた意思決定支援
```

### 5. 歯科医院での活用例

```
【リコール自動化】
AI:
  1. 定期検診対象患者を抽出（DBツール）
  2. 患者ごとの最適な連絡タイミングを判断
  3. LINE/SMSでリマインド送信（APIツール）
  4. 予約状況を追跡
  5. 未予約者へのフォローアップ

【問い合わせ対応】
患者: 「親知らずの抜歯は痛いですか？」
AI:
  1. 医院のFAQデータベースを検索（RAG）
  2. 過去の説明内容を参照
  3. 適切な回答を生成
  4. 必要に応じて予約を促す
```

## 注意点・課題

### 1. LangChain の変化の速さ

```
問題:
・APIが頻繁に変わる
・半年前の情報が古くなる
・バージョン間の互換性問題

対策:
・基本概念を理解し、変化に対応できる力をつける
・公式ドキュメントを常に参照
・バージョンを固定して安定運用
```

### 2. 精度・信頼性（ハルシネーション）

```
問題:
・AIは間違える（もっともらしい嘘をつく）
・重要な判断を完全自動化するリスク
・責任の所在が曖昧になる

対策:
・「AIが提案 → 人間が承認」のフローを基本とする
・RAGで根拠となる文書を明示
・重要度に応じた承認レベルを設定
・ログを残して追跡可能にする
```

### 3. セキュリティ

```
問題:
・社内文書をLLMに送る → 情報漏洩リスク
・プロンプトインジェクション攻撃
・APIキーの管理

対策:
・機密情報のマスキング処理
・入力のサニタイズ（不正なプロンプトの除去）
・Azure OpenAI / AWS Bedrock 等のエンタープライズ向けサービス検討
・APIキーの環境変数管理、ローテーション
```

### 4. 導入の前提条件

```
プラチナを始める前に必要なこと:
・シルバー・ゴールドの修了（基盤構築）
・データの整備（RAG対象となる文書）
・業務フローの明確化（何を自動化するか）
・経営層の理解（AIの限界と可能性）
```
