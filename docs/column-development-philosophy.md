# コラム：中小企業の内製開発と「伽藍とバザール」

## はじめに

エリック・レイモンドが1997年に発表した「伽藍とバザール」は、ソフトウェア開発の二つのモデルを対比した有名なエッセイです。この考え方は、中小企業がAI伴走型で内製開発を行う際にも重要な示唆を与えてくれます。

---

## 二つの開発モデル

### 伽藍モデル（Cathedral）

```
少数の精鋭が、綿密に計画し、完成してからリリースする

【特徴】
・要件定義 → 設計 → 実装 → テスト → 納品
・すべてが計画通りに進むことを前提
・完成するまでユーザーは触れない
・変更には大きなコストがかかる

【メリット】
・品質が計画的に管理される
・大規模プロジェクトで実績がある

【デメリット】
・高コスト、長期間
・完成してから「思っていたのと違う」が起きる
・変更するたびに追加費用
```

### バザールモデル（Bazaar）

```
多くの人が参加し、早期・頻繁にリリースして改善を繰り返す

【特徴】
・まず動くものを作って公開する
・ユーザーからのフィードバックで改善
・「早めのリリース、しょっちゅうリリース」
・ユーザーを共同開発者として扱う

【メリット】
・フィードバックが早い
・ユーザーのニーズに合いやすい
・問題が早期に発見される

【デメリット】
・大きなコミュニティが前提
・品質管理が難しい場合がある
```

## 中小企業の内製開発はどちらか？

### 結論：どちらでもない「第三のモデル」

```
┌─────────────────────────────────────────────────────────┐
│              ソフトウェア開発のスペクトラム              │
│                                                         │
│  伽藍            ←── AI伴走型内製 ──→          バザール│
│  (SIer)           (今回のカリキュラム)          (OSS)   │
│                                                         │
│  計画的            実用的              コミュニティ主導  │
│  高コスト          低コスト            ボランティア      │
│  変更困難          即座に変更          フォーク可能      │
│  専門家が開発      ユーザーが開発      多数が開発        │
│  完璧を目指す      動けばOK            継続的改善        │
│  販売価値          利用価値            利用価値          │
└─────────────────────────────────────────────────────────┘
```

## バザールから学ぶ3つの原則

### 原則1：「早めのリリース、しょっちゅうリリース」

```
【伽藍型（SIer発注）】
半年かけて完璧に作る → 現場に合わない → 修正に追加費用

【バザール的アプローチ（AI伴走型内製）】
1週間でMVP → 現場で使う → 翌日改善 → また使う → また改善

なぜこれが中小企業に合うのか:
・AIがあるから修正が即座にできる
・完璧を目指さず、使いながら育てる
・現場の声をすぐ反映できる
```

カリキュラムのシルバー第6部（実践プロジェクト）やプラチナ第7部がまさにこのアプローチです。最初から完璧なアプリを作るのではなく、最小限の機能で使い始め、フィードバックを受けて改善していきます。

### 原則2：「ユーザーを共同開発者として扱え」

```
【伽藍型】
ユーザー ≠ 開発者（明確に分離）
→ 要件のズレが発生する

【SIerに依頼した場合の典型的な問題】
営業「こういう機能がほしい」
→ SE「こう解釈しました」
→ プログラマ「こう実装しました」
→ 営業「思っていたのと違う…」

【AI伴走型内製】
ユーザー ＝ 開発者（同一人物）
→ 要件のズレが原理的に発生しない

営業「こういう機能がほしい」
→ 営業（自分で）「Claude、この機能を作って」
→ 営業「ここをこう変えて」
→ 営業「これでOK」
```

バザールモデルでは「ユーザーを共同開発者として扱う」ことが重要ですが、今回のカリキュラムでは **ユーザーが開発者そのもの** です。これはバザールよりもさらに密なフィードバックループです。

### 原則3：「目玉の数さえ十分あれば、どんなバグも深刻ではない」

```
【バザール（OSSコミュニティ）】
多数の開発者がコードを読む → バグが見つかる
= 「リーナスの法則」

【中小企業の現実】
開発者は1〜2名 → 目玉の数が足りない

【AI伴走型の解決策】
AIがコードレビュー → バグが見つかる
= 「人工的なリーナスの法則」

・GitHub Copilot が「24時間稼働のレビュアー」
・エラーが出たらAIに聞く → 即座に原因特定
・テストコードもAIが生成 → 自動で品質チェック
```

人間のレビュアーは確保できなくても、AIが「追加の目玉」として機能します。さらに自動テストを組み合わせることで、少人数でも品質を維持できます。

## 伽藍から学ぶ2つの原則

バザール的なアプローチだけでは不十分な領域もあります。

### 原則1：データベース設計は計画的に

```
【バザール的に進めてはいけないもの】
・テーブル設計（後から変更すると影響が大きい）
・認証・権限設計（セキュリティに直結）
・データの整合性ルール

→ これらは最初にしっかり設計する
→ 伽藍的な「計画」が必要

【バザール的に進めてよいもの】
・画面のレイアウト
・操作フロー
・表示する情報の選択

→ これらは使いながら改善できる
```

### 原則2：品質の基準は決めておく

```
【「動けばOK」では済まないもの】
・決済処理（お金に関わる）
・顧客データの保護（個人情報）
・認証・認可（セキュリティ）

→ テスト自動化で品質を担保
→ AIによるコードレビューを習慣化
→ 「動くかどうか」ではなく「正しいかどうか」

※ カリキュラムでは各ステージで品質確保の方法を学ぶ
```

## IPAの「DXステージ」との関係

IPA（情報処理推進機構）のDXレポートでは、DXを段階的に整理しています。各段階で適した開発アプローチが異なります。

### 要件定義の難しさとDXステージ

| DXステージ | 要件の明確さ | 適した手法 | カリキュラム |
|---|---|---|---|
| デジタイゼーション | ◎ 明確 | 伽藍でも可 | ブロンズ |
| デジタライゼーション | ○ 比較的明確 | バザール的反復 | シルバー・ゴールド |
| DX（競争力強化） | △ 不明確 | 必ずバザール的に | プラチナ |

### 競争力強化ステージの特殊性

```
【ブロンズ・シルバー（デジタイゼーション/デジタライゼーション）】
・「月次集計を自動化したい」→ 要件は明確
・「紙の申請をWebにしたい」→ 要件は明確
・やることが分かっている → 計画を立てやすい

【プラチナ（競争力強化）】
・「リピート率を上げたい」→ 何をすればいいか不明確
・「顧客体験を良くしたい」→ 正解が事前に分からない
・クーポンの割引率は？タイミングは？ → 試してみないと分からない

→ 壮大な計画を立てて大きな投資をしてもうまくいかない
→ 小さく試して、データで検証して、改善する
→ これはバザール的な「早めのリリース、しょっちゅうリリース」そのもの
```

## AI伴走型内製開発 = 「個人工房 + AI助手」モデル

### 従来モデルとの比較

```
【伽藍（SIer）】
・建築で言えば「ゼネコンに依頼して高層ビルを建てる」
・設計図通りに作る。変更は困難で高コスト
・品質は管理されるが、融通が利かない

【バザール（OSS）】
・建築で言えば「みんなで街を作る」
・参加自由。良いものが自然と残る
・多様性があるが、統一感に欠ける場合も

【AI伴走型内製（今回のカリキュラム）】
・建築で言えば「自分で家を建てる。AIが設計と施工を手伝う」
・住む人が作るから、自分に合った家になる
・AIが専門知識を補う
・小さく始めて、住みながら増築できる
```

### このモデルが中小企業に最適な理由

```
1. コスト
   ・伽藍（SIer）: 初期300万円〜 + 保守月5〜10万円
   ・バザール: ボランティアだが、自社専用品は作られない
   ・AI伴走型: 教育費 + ツール月数千円

2. スピード
   ・伽藍: 要件定義〜納品まで3〜6ヶ月
   ・バザール: コミュニティの合意が必要
   ・AI伴走型: 作りたいと思ったその日に着手

3. フィット感
   ・伽藍: 要件定義のズレが発生しやすい
   ・バザール: 汎用的になりがち
   ・AI伴走型: ユーザー＝開発者なのでズレがない

4. 持続性
   ・伽藍: SIerに依存し続ける
   ・バザール: コミュニティが消滅するリスク
   ・AI伴走型: 自社にスキルが蓄積される
```

## 「魔法のおなべ」の教訓

レイモンドのもう一つのエッセイ「魔法のおなべ」では、ソフトウェアの価値を「利用価値」と「販売価値」に分けています。

```
【販売価値】
・パッケージソフト、SaaSなど
・作って売ることで利益を得る
・市場が大きいほど投資が回収できる

【利用価値】
・自社で使うために作るソフトウェア
・売る必要がない
・「使える」ことが価値のすべて
```

レイモンドは「ソフトウェアの95%は販売されず、利用のために書かれている」と述べています。

**中小企業の業務アプリは、100%が「利用価値」のソフトウェアです。**

```
【利用価値型に必要なもの】
✓ 自社の業務に合っていること
✓ すぐに修正できること
✓ 低コストで運用できること

✗ 美しいUI/UXは最優先ではない
✗ 大規模なスケーラビリティは不要
✗ 完璧なアーキテクチャは不要

→ 「使える」ことが最も重要
→ 完璧さよりも実用性
→ だからバザール的な反復開発が合う
```
