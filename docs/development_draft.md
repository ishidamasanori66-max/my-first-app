# Aratana開発手法ドラフト

本ドキュメントは、Aratanaメソッドにおける開発手法の検討資料です。

---

## 主な「◯◯駆動開発」の比較

| 手法 | 焦点 | Aratana適合性 |
|---|---|---|
| **テスト駆動開発（TDD）** | テストを先に書く | △ 初学者には負荷高い |
| **ドメイン駆動設計（DDD）** | ビジネスドメインのモデル化 | △ 概念は有用だが複雑すぎる |
| **振る舞い駆動開発（BDD）** | ユーザーの振る舞い記述 | △ Given-When-Then記法は有用 |
| **データ駆動開発** | データ構造を先に設計 | ◎ DB設計重視と一致 |
| **機能駆動開発（FDD）** | 機能単位で開発 | ○ 実用的 |

## Aratana流：「業務データ駆動開発」の提案

DDDの本質を取り入れつつ、中小企業向けに簡略化した手法です。

### 基本サイクル

```
┌───────────────────────────────────────────────────────────────────┐
│                                                                   │
│   1. 業務を聞く → 2. データを決める → 2.5 モックで検証            │
│         ↑                                         ↓              │
│         │                              3. AIと作る               │
│         │                                         │              │
│         └─────────── 4. 使って改善 ←──────────────┘              │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

※ Phase 2.5「モックで検証」は、HTMXで動く画面を素早く作り、現場で触って確認するフェーズ

### 各フェーズの詳細

#### Phase 1：業務を聞く（ヒアリング駆動）

```
【やること】
・経営層/現場に「何を知りたいか」「何に困っているか」を聞く
・業務で使っている言葉（用語）をそのまま記録
・既存のExcel/紙帳票を収集

【成果物】
・業務用語リスト（glossary）
・現状の業務フロー図
・「こうなったら嬉しい」リスト

【DDDからの借用】
・ユビキタス言語 → 業務用語をそのままコードに使う
・ドメインエキスパート → 現場の担当者と対話
```

#### Phase 2：データを決める（データモデル駆動）

```
【やること】
・「何を記録すべきか」を決める
・テーブル設計（ER図）を描く
・カラム名はローマ字で業務用語を使う

【成果物】
・ER図（テーブル関連図）
・テーブル定義書（用語集付き）

【ポイント】
・ここが最も重要（AIに代替されない）
・経営層と「このデータがあれば判断できる」を確認
・設計が8割、実装は2割
```

#### Phase 3：AIと作る（AI伴走開発）

```
【やること】
・設計書をもとにAI（Copilot/Claude）と対話
・「shohinテーブルのCRUDを作って」と指示
・AIの出力をレビュー・修正

【ポイント】
・ローマ字命名なので、AIが既存コードを尊重
・設計原則（DRY/KISS/YAGNI）で出力を評価
・テストもAIに書かせる
```

#### Phase 4：使って改善（フィードバック駆動）

```
【やること】
・実際に業務で使ってもらう
・「ここも記録したい」「この集計も見たい」を収集
・Phase 1に戻る

【ポイント】
・一発で完璧を目指さない
・小さく作って、使いながら育てる
・経営層との対話を継続
```

## TDD（テスト駆動開発）をどう扱うか

```
【本格的なTDDは採用しない理由】
・「テストを先に書く」は初学者には認知負荷が高い
・中小企業の業務アプリは、まず動くことが優先

【代わりに採用する手法】
・AIにテストを書かせる（実装後）
・CIで自動テスト実行
・「テストがないと本番に出せない」文化を作る

【シルバー以降で教えること】
・pytest の基本
・GitHub Actions での自動テスト
・AIへの指示：「このビューのテストを書いて」
```

---

## BDD（振る舞い駆動開発）をどう扱うか

```
【Given-When-Then の考え方は有用】
・要件定義の言語化に使える
・経営層との会話で使える

【例】
Given: 顧客が過去3ヶ月来店していない
When: 月末のバッチ処理が実行される
Then: その顧客にリマインドメールが送信される

【ただし】
・フレームワーク（Cucumber等）は導入しない
・「考え方」として教える程度でOK
```

## 各手法からの借用まとめ

| 要素 | 採用する内容 | 採用しない内容 |
|---|---|---|
| **DDD** | 業務用語の統一、ドメイン重視 | 集約、リポジトリ、複雑なパターン |
| **TDD** | AIにテストを書かせる、CI自動化 | テストファースト |
| **BDD** | Given-When-Thenの考え方 | Cucumberなどのフレームワーク |
| **データ駆動** | DB設計を最初にしっかり行う | - |

## AppSheetが証明する「データ駆動」

### AppSheetの開発フロー

```
【AppSheetの基本フロー】
1. データを用意する（Google Sheets / Excel / DB）
    ↓
2. AppSheetがデータ構造を読み取る
    ↓
3. CRUD画面を自動生成（一覧・詳細・入力フォーム）
    ↓
4. 必要に応じてカスタマイズ（UI調整、ロジック追加）
```

### つまり「データ駆動」そのもの

| 工程 | AppSheetでの作業 |
|---|---|
| **データ設計** | スプレッドシートの列名・型を決める |
| **画面設計** | 自動生成（ほぼ不要） |
| **ロジック実装** | 条件式・ワークフローを設定 |
| **コーディング** | **不要** |

### これが意味すること

```
【AppSheetが証明していること】
・「データ構造が決まれば、アプリの8割は決まる」
・画面やCRUDは自動化できる
・人間が考えるべきは「何のデータを、どう持つか」

【Aratana開発手法との整合性】
・Phase 2「データを決める」が最重要という考え方と一致
・AppSheetは「データ駆動開発」の最も純粋な形
```

### カリキュラムとの接続

```
【シルバーの流れ】
AppSheet（データ駆動・ノーコード）
    ↓
Django（データ駆動・コードあり）

【共通点】
・どちらも「データ構造」から始まる
・AppSheet: スプレッドシート設計 → 自動生成
・Django: モデル定義 → Admin自動生成 + HTMX画面

【違い】
・AppSheet: カスタマイズに限界あり
・Django: 自由度が高いが、コードが必要
```

## HTMXモック駆動：早期検証のアプローチ

### 従来の問題

```
【従来のウォーターフォール】
要件定義 → 画面設計（Figma等）→ 実装 → テスト → 修正
                ↑
            ここで認識ズレが発覚（手戻り大）

【提案：モック駆動】
データ設計 → HTMXモック → 触って検証 → 修正 → 本実装
                  ↑
            動くもので確認（手戻り小）
```

### Djangoでのモック作成が速い理由

```python
# 1. モデル定義（5分）
class Chumon(models.Model):
    kokyaku = models.ForeignKey(Kokyaku, on_delete=models.CASCADE)
    chumon_date = models.DateField()
    status = models.CharField(max_length=20)

# 2. 自動生成されるもの
# - Django Admin（管理者用、即座に使える）
# - ModelForm（入力フォーム）
# - ListView / DetailView（一覧・詳細）
```

```html
<!-- 3. HTMXで動的UI（30分）-->
<form hx-post="/chumon/create/" hx-target="#result">
  {{ form.as_p }}
  <button type="submit">登録</button>
</form>
<div id="result"></div>

<!-- 一覧の動的更新 -->
<div hx-get="/chumon/list/" hx-trigger="load">
  読み込み中...
</div>
```

### モック段階で検証できること

| 検証項目 | モックで確認 |
|---|---|
| **データの過不足** | 「この項目も必要」「これは不要」 |
| **操作の流れ** | 「登録してから一覧に戻りたい」 |
| **表示順・絞り込み** | 「日付順に並べたい」 |
| **入力の手間** | 「選択肢が多すぎる」 |

### AppSheet vs HTMXモック

| 観点 | AppSheet | HTMXモック |
|---|---|---|
| 作成速度 | ◎ 数分 | ○ 数時間 |
| カスタマイズ | △ 限界あり | ◎ 自由 |
| 本実装への移行 | × 作り直し | ◎ そのまま拡張 |
| 学習コスト | ○ 低い | ○ シルバーで習得済み |

```
【ポイント】
・AppSheet：使い捨てプロトタイプ（シルバー初期）
・HTMXモック：本実装の土台になる（シルバー中盤以降）

→ シルバー以降は「HTMXモック」の方が効率的
```

### 開発フローへの組み込み（改訂版）

```
Phase 1: 業務を聞く
    ↓
Phase 2: データを決める（モデル定義）
    ↓
Phase 2.5: HTMXモックで検証 ← 追加
    ↓
Phase 3: AIと作る（本実装）
    ↓
Phase 4: 使って改善
```

### Phase 2.5 の具体的な作業

```
【やること】
1. Djangoモデルを定義（makemigrations / migrate）
2. 最小限のビュー + HTMXで画面を作る
3. 現場担当者に触ってもらう
4. フィードバックを受けてデータ設計を修正

【所要時間】
・小規模アプリ：半日〜1日
・中規模アプリ：2〜3日

【ツール】
・スタイリングはTailwind CSS（またはPico CSS）で最小限
・動作確認が目的なので、見た目は二の次
```

## AppSheetのワークフロー機能：出張管理システムを例に

### 検討事例：出張申請・承認・清算システム

```
【業務フロー】
出張申請 → 上長承認 → 出張実施 → 清算申請 → 清算承認 → 完了
```

### AppSheetのワークフロー機能

| 機能 | AppSheetでの実現 |
|---|---|
| ステータス管理 | ◎ 列で管理（申請中/承認済/却下等） |
| 承認ボタン | ◎ Action ボタンで実装 |
| 通知 | ◎ Automation で Email/プッシュ通知 |
| 権限制御 | ○ User Role で制御 |
| 条件分岐 | ○ 条件式で実装可能 |

### データ構造の例

```
【データ構造（Google Sheets）】

シート1: 出張申請
├─ shinsei_id（申請ID）
├─ shinseisha（申請者）
├─ shutcho_saki（出張先）
├─ shuppatsu_date / kitaku_date（出発日/帰着日）
├─ mokuteki（目的）
├─ gaisan_hiyo（概算費用）
├─ status（申請中/承認済/却下/清算待ち/完了）
└─ shounin_sha / shounin_date（承認者/承認日）

シート2: 清算明細
├─ meisai_id（明細ID）
├─ shinsei_id（申請ID：リレーション）
├─ himoku（費目：交通費/宿泊費/日当等）
├─ kingaku（金額）
├─ ryoshusho_image（領収書画像）
└─ status
```

### AppSheet Automation での実装

```
【ワークフロー自動化】

1. 申請時
   → 上長にメール通知
   → status = "shinsei_chu"

2. 承認ボタン押下時
   → status = "shounin_zumi"
   → 申請者に通知

3. 出張完了後、清算申請
   → 明細追加画面を表示
   → status = "seisan_machi"

4. 清算承認
   → status = "kanryo"
   → 経理に通知
```

### AppSheetの限界

| 要件 | 実現度 | 課題 |
|---|---|---|
| **単純な承認フロー** | ◎ | 問題なし |
| **多段階承認**（係長→課長→部長） | △ | 実装は可能だが複雑になる |
| **並列承認**（AとB両方の承認が必要） | △ | 条件式が複雑化 |
| **代理承認** | △ | ユーザー管理が煩雑 |
| **差し戻し→再申請** | ○ | ステータス遷移で対応 |
| **監査ログ** | △ | 別シートで手動記録が必要 |
| **外部連携**（経費精算システム等） | × | API連携は困難 |

### 判断基準：AppSheet vs Django

```
【AppSheetで十分なケース】
・承認者が1〜2段階
・ユーザー数が少ない（〜50人程度）
・社内利用のみ
・複雑な条件分岐がない
・外部システム連携が不要

【Djangoが必要なケース】
・承認フローが複雑（多段階、並列、条件分岐）
・監査ログが必須
・外部システムとの連携が必要
・カスタマイズ要件が多い
・将来的な拡張が見込まれる
```

### シルバーカリキュラムとの接続

```
【提案：2段階アプローチ】

Phase 1: AppSheetでプロトタイプ
・基本的なワークフローを素早く構築
・現場で使ってもらい、要件を洗い出す
・「こういう機能も欲しい」を収集

Phase 2: Djangoで本実装（必要に応じて）
・AppSheetの限界に達したら移行
・または最初からDjangoで良い場合もある
```

### Djangoでのワークフロー実装例

```python
# シンプルなステータス遷移
class ShutchoShinsei(models.Model):
    STATUS_CHOICES = [
        ('draft', '下書き'),
        ('pending', '申請中'),
        ('approved', '承認済'),
        ('rejected', '却下'),
        ('settlement', '清算待ち'),
        ('completed', '完了'),
    ]

    shinseisha = models.ForeignKey(User, on_delete=models.CASCADE)
    shutcho_saki = models.CharField(max_length=100)
    status = models.CharField(max_length=20, choices=STATUS_CHOICES)
    shounin_sha = models.ForeignKey(User, null=True, blank=True,
                                     on_delete=models.SET_NULL,
                                     related_name='shounin_set')
    shounin_date = models.DateTimeField(null=True, blank=True)
```

```python
# 承認アクション
def shounin(request, shinsei_id):
    shinsei = ShutchoShinsei.objects.get(id=shinsei_id)
    shinsei.status = 'approved'
    shinsei.shounin_sha = request.user
    shinsei.shounin_date = timezone.now()
    shinsei.save()

    # 通知送信
    send_notification(shinsei.shinseisha, "出張申請が承認されました")

    return redirect('shinsei_list')
```

### ワークフロー機能の比較まとめ

| 観点 | AppSheet | Django |
|---|---|---|
| 開発速度 | ◎ 数時間 | ○ 数日 |
| 単純ワークフロー | ◎ | ◎ |
| 複雑ワークフロー | △ | ◎ |
| カスタマイズ | △ | ◎ |
| 外部連携 | × | ◎ |
| 推奨用途 | プロトタイプ/小規模 | 本格運用 |

```
【結論】
・出張管理のような「単純な承認フロー」はAppSheetで十分実現可能
・ただし、複雑化する見込みがあるなら、最初からDjango + HTMXで作る方が手戻りが少ない
・AppSheetで要件を洗い出し → Djangoで本実装 という2段階も有効
```

