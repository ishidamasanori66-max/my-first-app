# Aratana開発手法ドラフト

本ドキュメントは、Aratanaメソッドにおける開発手法の検討資料です。

---

## 主な「◯◯駆動開発」の比較

| 手法 | 焦点 | Aratana適合性 |
|---|---|---|
| **テスト駆動開発（TDD）** | テストを先に書く | △ 初学者には負荷高い |
| **ドメイン駆動設計（DDD）** | ビジネスドメインのモデル化 | △ 概念は有用だが複雑すぎる |
| **振る舞い駆動開発（BDD）** | ユーザーの振る舞い記述 | △ Given-When-Then記法は有用 |
| **データ駆動開発** | データ構造を先に設計 | ◎ DB設計重視と一致 |
| **機能駆動開発（FDD）** | 機能単位で開発 | ○ 実用的 |

## Aratana流：「業務データ駆動開発」の提案

DDDの本質を取り入れつつ、中小企業向けに簡略化した手法です。

### 基本サイクル

```
┌───────────────────────────────────────────────────────────────────┐
│                                                                   │
│   1. 業務を聞く → 2. データを決める → 2.5 モックで検証            │
│         ↑                                         ↓              │
│         │                              3. AIと作る               │
│         │                                         │              │
│         └─────────── 4. 使って改善 ←──────────────┘              │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

※ Phase 2.5「モックで検証」は、HTMXで動く画面を素早く作り、現場で触って確認するフェーズ

### 各フェーズの詳細

#### Phase 1：業務を聞く（ヒアリング駆動）

```
【やること】
・経営層/現場に「何を知りたいか」「何に困っているか」を聞く
・業務で使っている言葉（用語）をそのまま記録
・既存のExcel/紙帳票を収集

【成果物】
・業務用語リスト（glossary）
・現状の業務フロー図
・「こうなったら嬉しい」リスト

【DDDからの借用】
・ユビキタス言語 → 業務用語をそのままコードに使う
・ドメインエキスパート → 現場の担当者と対話
```

#### Phase 2：データを決める（データモデル駆動）

```
【やること】
・「何を記録すべきか」を決める
・テーブル設計（ER図）を描く
・カラム名はローマ字で業務用語を使う

【成果物】
・ER図（テーブル関連図）
・テーブル定義書（用語集付き）

【ポイント】
・ここが最も重要（AIに代替されない）
・経営層と「このデータがあれば判断できる」を確認
・設計が8割、実装は2割
```

#### Phase 3：AIと作る（AI伴走開発）

```
【やること】
・設計書をもとにAI（Copilot/Claude）と対話
・「shohinテーブルのCRUDを作って」と指示
・AIの出力をレビュー・修正

【ポイント】
・ローマ字命名なので、AIが既存コードを尊重
・設計原則（DRY/KISS/YAGNI）で出力を評価
・テストもAIに書かせる
```

#### Phase 4：使って改善（フィードバック駆動）

```
【やること】
・実際に業務で使ってもらう
・「ここも記録したい」「この集計も見たい」を収集
・Phase 1に戻る

【ポイント】
・一発で完璧を目指さない
・小さく作って、使いながら育てる
・経営層との対話を継続
```

## TDD（テスト駆動開発）をどう扱うか

```
【本格的なTDDは採用しない理由】
・「テストを先に書く」は初学者には認知負荷が高い
・中小企業の業務アプリは、まず動くことが優先

【代わりに採用する手法】
・AIにテストを書かせる（実装後）
・CIで自動テスト実行
・「テストがないと本番に出せない」文化を作る

【シルバー以降で教えること】
・pytest の基本
・GitHub Actions での自動テスト
・AIへの指示：「このビューのテストを書いて」
```

---

## BDD（振る舞い駆動開発）をどう扱うか

```
【Given-When-Then の考え方は有用】
・要件定義の言語化に使える
・経営層との会話で使える

【例】
Given: 顧客が過去3ヶ月来店していない
When: 月末のバッチ処理が実行される
Then: その顧客にリマインドメールが送信される

【ただし】
・フレームワーク（Cucumber等）は導入しない
・「考え方」として教える程度でOK
```

## 各手法からの借用まとめ

| 要素 | 採用する内容 | 採用しない内容 |
|---|---|---|
| **DDD** | 業務用語の統一、ドメイン重視 | 集約、リポジトリ、複雑なパターン |
| **TDD** | AIにテストを書かせる、CI自動化 | テストファースト |
| **BDD** | Given-When-Thenの考え方 | Cucumberなどのフレームワーク |
| **データ駆動** | DB設計を最初にしっかり行う | - |

## AppSheetが証明する「データ駆動」

### AppSheetの開発フロー

```
【AppSheetの基本フロー】
1. データを用意する（Google Sheets / Excel / DB）
    ↓
2. AppSheetがデータ構造を読み取る
    ↓
3. CRUD画面を自動生成（一覧・詳細・入力フォーム）
    ↓
4. 必要に応じてカスタマイズ（UI調整、ロジック追加）
```

### つまり「データ駆動」そのもの

| 工程 | AppSheetでの作業 |
|---|---|
| **データ設計** | スプレッドシートの列名・型を決める |
| **画面設計** | 自動生成（ほぼ不要） |
| **ロジック実装** | 条件式・ワークフローを設定 |
| **コーディング** | **不要** |

### これが意味すること

```
【AppSheetが証明していること】
・「データ構造が決まれば、アプリの8割は決まる」
・画面やCRUDは自動化できる
・人間が考えるべきは「何のデータを、どう持つか」

【Aratana開発手法との整合性】
・Phase 2「データを決める」が最重要という考え方と一致
・AppSheetは「データ駆動開発」の最も純粋な形
```

### カリキュラムとの接続

```
【シルバーの流れ】
AppSheet（データ駆動・ノーコード）
    ↓
Django（データ駆動・コードあり）

【共通点】
・どちらも「データ構造」から始まる
・AppSheet: スプレッドシート設計 → 自動生成
・Django: モデル定義 → Admin自動生成 + HTMX画面

【違い】
・AppSheet: カスタマイズに限界あり
・Django: 自由度が高いが、コードが必要
```

## HTMXモック駆動：早期検証のアプローチ

### 従来の問題

```
【従来のウォーターフォール】
要件定義 → 画面設計（Figma等）→ 実装 → テスト → 修正
                ↑
            ここで認識ズレが発覚（手戻り大）

【提案：モック駆動】
データ設計 → HTMXモック → 触って検証 → 修正 → 本実装
                  ↑
            動くもので確認（手戻り小）
```

### Djangoでのモック作成が速い理由

```python
# 1. モデル定義（5分）
class Chumon(models.Model):
    kokyaku = models.ForeignKey(Kokyaku, on_delete=models.CASCADE)
    chumon_date = models.DateField()
    status = models.CharField(max_length=20)

# 2. 自動生成されるもの
# - Django Admin（管理者用、即座に使える）
# - ModelForm（入力フォーム）
# - ListView / DetailView（一覧・詳細）
```

```html
<!-- 3. HTMXで動的UI（30分）-->
<form hx-post="/chumon/create/" hx-target="#result">
  {{ form.as_p }}
  <button type="submit">登録</button>
</form>
<div id="result"></div>

<!-- 一覧の動的更新 -->
<div hx-get="/chumon/list/" hx-trigger="load">
  読み込み中...
</div>
```

### モック段階で検証できること

| 検証項目 | モックで確認 |
|---|---|
| **データの過不足** | 「この項目も必要」「これは不要」 |
| **操作の流れ** | 「登録してから一覧に戻りたい」 |
| **表示順・絞り込み** | 「日付順に並べたい」 |
| **入力の手間** | 「選択肢が多すぎる」 |

### AppSheet vs HTMXモック

| 観点 | AppSheet | HTMXモック |
|---|---|---|
| 作成速度 | ◎ 数分 | ○ 数時間 |
| カスタマイズ | △ 限界あり | ◎ 自由 |
| 本実装への移行 | × 作り直し | ◎ そのまま拡張 |
| 学習コスト | ○ 低い | ○ シルバーで習得済み |

```
【ポイント】
・AppSheet：使い捨てプロトタイプ（シルバー初期）
・HTMXモック：本実装の土台になる（シルバー中盤以降）

→ シルバー以降は「HTMXモック」の方が効率的
```

### 開発フローへの組み込み（改訂版）

```
Phase 1: 業務を聞く
    ↓
Phase 2: データを決める（モデル定義）
    ↓
Phase 2.5: HTMXモックで検証 ← 追加
    ↓
Phase 3: AIと作る（本実装）
    ↓
Phase 4: 使って改善
```

### Phase 2.5 の具体的な作業

```
【やること】
1. Djangoモデルを定義（makemigrations / migrate）
2. 最小限のビュー + HTMXで画面を作る
3. 現場担当者に触ってもらう
4. フィードバックを受けてデータ設計を修正

【所要時間】
・小規模アプリ：半日〜1日
・中規模アプリ：2〜3日

【ツール】
・スタイリングはTailwind CSS（またはPico CSS）で最小限
・動作確認が目的なので、見た目は二の次
```

## AppSheetのワークフロー機能：出張管理システムを例に

### 検討事例：出張申請・承認・清算システム

```
【業務フロー】
出張申請 → 上長承認 → 出張実施 → 清算申請 → 清算承認 → 完了
```

### AppSheetのワークフロー機能

| 機能 | AppSheetでの実現 |
|---|---|
| ステータス管理 | ◎ 列で管理（申請中/承認済/却下等） |
| 承認ボタン | ◎ Action ボタンで実装 |
| 通知 | ◎ Automation で Email/プッシュ通知 |
| 権限制御 | ○ User Role で制御 |
| 条件分岐 | ○ 条件式で実装可能 |

### データ構造の例

```
【データ構造（Google Sheets）】

シート1: 出張申請
├─ shinsei_id（申請ID）
├─ shinseisha（申請者）
├─ shutcho_saki（出張先）
├─ shuppatsu_date / kitaku_date（出発日/帰着日）
├─ mokuteki（目的）
├─ gaisan_hiyo（概算費用）
├─ status（申請中/承認済/却下/清算待ち/完了）
└─ shounin_sha / shounin_date（承認者/承認日）

シート2: 清算明細
├─ meisai_id（明細ID）
├─ shinsei_id（申請ID：リレーション）
├─ himoku（費目：交通費/宿泊費/日当等）
├─ kingaku（金額）
├─ ryoshusho_image（領収書画像）
└─ status
```

### AppSheet Automation での実装

```
【ワークフロー自動化】

1. 申請時
   → 上長にメール通知
   → status = "shinsei_chu"

2. 承認ボタン押下時
   → status = "shounin_zumi"
   → 申請者に通知

3. 出張完了後、清算申請
   → 明細追加画面を表示
   → status = "seisan_machi"

4. 清算承認
   → status = "kanryo"
   → 経理に通知
```

### AppSheetの限界

| 要件 | 実現度 | 課題 |
|---|---|---|
| **単純な承認フロー** | ◎ | 問題なし |
| **多段階承認**（係長→課長→部長） | △ | 実装は可能だが複雑になる |
| **並列承認**（AとB両方の承認が必要） | △ | 条件式が複雑化 |
| **代理承認** | △ | ユーザー管理が煩雑 |
| **差し戻し→再申請** | ○ | ステータス遷移で対応 |
| **監査ログ** | △ | 別シートで手動記録が必要 |
| **外部連携**（経費精算システム等） | × | API連携は困難 |

### 判断基準：AppSheet vs Django

```
【AppSheetで十分なケース】
・承認者が1〜2段階
・ユーザー数が少ない（〜50人程度）
・社内利用のみ
・複雑な条件分岐がない
・外部システム連携が不要

【Djangoが必要なケース】
・承認フローが複雑（多段階、並列、条件分岐）
・監査ログが必須
・外部システムとの連携が必要
・カスタマイズ要件が多い
・将来的な拡張が見込まれる
```

### シルバーカリキュラムとの接続

```
【提案：2段階アプローチ】

Phase 1: AppSheetでプロトタイプ
・基本的なワークフローを素早く構築
・現場で使ってもらい、要件を洗い出す
・「こういう機能も欲しい」を収集

Phase 2: Djangoで本実装（必要に応じて）
・AppSheetの限界に達したら移行
・または最初からDjangoで良い場合もある
```

### Djangoでのワークフロー実装例

```python
# シンプルなステータス遷移
class ShutchoShinsei(models.Model):
    STATUS_CHOICES = [
        ('draft', '下書き'),
        ('pending', '申請中'),
        ('approved', '承認済'),
        ('rejected', '却下'),
        ('settlement', '清算待ち'),
        ('completed', '完了'),
    ]

    shinseisha = models.ForeignKey(User, on_delete=models.CASCADE)
    shutcho_saki = models.CharField(max_length=100)
    status = models.CharField(max_length=20, choices=STATUS_CHOICES)
    shounin_sha = models.ForeignKey(User, null=True, blank=True,
                                     on_delete=models.SET_NULL,
                                     related_name='shounin_set')
    shounin_date = models.DateTimeField(null=True, blank=True)
```

```python
# 承認アクション
def shounin(request, shinsei_id):
    shinsei = ShutchoShinsei.objects.get(id=shinsei_id)
    shinsei.status = 'approved'
    shinsei.shounin_sha = request.user
    shinsei.shounin_date = timezone.now()
    shinsei.save()

    # 通知送信
    send_notification(shinsei.shinseisha, "出張申請が承認されました")

    return redirect('shinsei_list')
```

### ワークフロー機能の比較まとめ

| 観点 | AppSheet | Django |
|---|---|---|
| 開発速度 | ◎ 数時間 | ○ 数日 |
| 単純ワークフロー | ◎ | ◎ |
| 複雑ワークフロー | △ | ◎ |
| カスタマイズ | △ | ◎ |
| 外部連携 | × | ◎ |
| 推奨用途 | プロトタイプ/小規模 | 本格運用 |

```
【結論】
・出張管理のような「単純な承認フロー」はAppSheetで十分実現可能
・ただし、複雑化する見込みがあるなら、最初からDjango + HTMXで作る方が手戻りが少ない
・AppSheetで要件を洗い出し → Djangoで本実装 という2段階も有効
```

## 利用者教育：アプリを「使ってもらう」までが開発

### なぜ利用者教育が必要か

```
【よくある失敗】
・アプリを作ったが「使い方が分からない」と言われる
・マニュアルがないので属人化する
・新入社員が来るたびに口頭で説明
・結局、元のExcelに戻ってしまう

→ 「作れる人」だけでなく「使い方を教えられる人」が必要
```

### 2つの教育ニーズ

| 用途 | 対象 | 内容 |
|---|---|---|
| **1. カリキュラム自体の配信** | DX推進担当者 | ブロンズ〜ダイヤモンドの教材 |
| **2. 作ったアプリの利用者教育** | 全社員 | 出張管理システムの使い方等 |

→ **用途2の方が切実**（作っても使われないとDX失敗）

### LMS（学習管理システム）の選択肢

| 選択肢 | コスト | 特徴 | Aratana適合性 |
|---|---|---|---|
| **Google Classroom** | 無料 | Google Workspace連携 | ○ AppSheetと同じエコシステム |
| **Moodle** | 無料（自前運用） | 高機能だが運用が重い | △ 管理負担大 |
| **Notion** | 無料〜 | ドキュメント+動画埋め込み | ○ 手軽 |
| **Django自作** | 開発コスト | 完全カスタマイズ | △ 車輪の再発明 |
| **Loom + Google Sites** | 無料〜安価 | 録画+簡易サイト | ◎ 最も手軽 |

### 推奨：段階的アプローチ

#### Phase 1：最小構成（すぐ始められる）

```
【ツール】
・Google Sites でマニュアルサイトを作成
・Loom（画面録画）で操作手順を録画
・アプリ内にヘルプリンクを設置

【作成するコンテンツ】
・スクリーンショット付き手順書
・3〜5分の操作動画
・FAQ（よくある質問）

→ LMSなしでも利用者教育は可能
```

#### Phase 2：中規模構成（社員50人以上）

```
【ツール】
・Google Classroom を活用

【メリット】
・コース形式で教材を整理
・進捗管理（誰が受講済みか把握）
・テスト/クイズで理解度確認
・新入社員に自動的にコースを割り当て
・Google Workspace を使っていれば追加コスト0
・モバイルからも受講可能
```

### 開発フローへの追加（最終版）

```
Phase 1: 業務を聞く
    ↓
Phase 2: データを決める（モデル定義）
    ↓
Phase 2.5: HTMXモックで検証
    ↓
Phase 3: AIと作る（本実装）
    ↓
Phase 4: 使って改善
    ↓
Phase 5: 利用者教育 ← 追加
    ├─ 操作マニュアル作成
    ├─ 操作動画の録画
    └─ 新入社員向けオンボーディング
```

### カリキュラムへの組み込み

```
【ゴールドで教えるべき内容】
・作ったアプリの利用者マニュアル作成
・Google Sites での公開方法
・Loom（画面録画ツール）の使い方
・Google Classroom でのコース作成（任意）

→ 「アプリを作る」だけでなく「使ってもらう」までが開発
```

### まとめ

| 観点 | 判断 |
|---|---|
| LMS導入 | **いきなり本格導入は過剰** |
| 利用者教育自体 | **必須**（作っただけでは使われない） |
| 推奨アプローチ | Google Sites + Loom → 必要に応じてGoogle Classroom |
| カリキュラムへの反映 | ゴールドに「利用者教育」を組み込み |

```
【DX成功の条件】
・良いアプリを作る（技術力）
・使い方を教える（教育力）
・継続的に改善する（運用力）

→ この3つが揃って初めてDXが定着する
```

## ブロンズでのER図作成：データ思考の基礎

### 提案：Excel自動化の前に業務を整理する

```
【現状のブロンズ】
Excel作業 → Python/SQLで自動化

【提案】
Excel作業 → ER図で整理 → Python/SQLで自動化
              ↑
         ここを追加
```

### なぜブロンズでER図か

| 観点 | 効果 |
|---|---|
| **業務の棚卸し** | 「何のデータが、どこにあるか」を可視化 |
| **データ思考の基礎** | 「まずデータを整理する」習慣がつく |
| **シルバーへの接続** | Django モデル設計にそのまま繋がる |
| **SQL学習の準備** | テーブル・カラム・リレーションの概念を先に理解 |
| **開発手法との一貫性** | 「業務データ駆動開発」のPhase 1, 2を体験 |

### 現場にすでに図がある場合

```
【確認すべきこと】
・業務フロー図はあるか？
・データ定義書はあるか？
・Excelファイルの一覧・関係図はあるか？

【ある場合】
→ それを活用し、不足部分を補完する
→ 既存資料を「ER図的な視点」で読み解く練習

```

### 具体的な例：複数店舗の売上集計業務

```
【Before（現状のExcel）】
├─ 店舗A_売上.xlsx
├─ 店舗B_売上.xlsx
├─ 店舗C_売上.xlsx
└─ 集計用.xlsx

↓ ER図で整理

【エンティティの抽出】
┌─────────┐       ┌─────────┐
│  tenpo   │──────│  uriage  │
│  店舗    │ 1  N │  売上    │
├─────────┤       ├─────────┤
│ tenpo_id │       │ uriage_id│
│ tenpo_mei│       │ tenpo_id │
│ chiiki   │       │ uriage_date│
└─────────┘       │ kingaku  │
                  └─────────┘

↓ これを見ながらSQL/Pythonで実装

【気づき】

・「店舗ID」で紐づいている
```

### ブロンズ向けに簡略化

```
【本格的なER図（複雑）】
・カーディナリティ記法（1:N, N:M）
・正規化理論（第1〜第3正規形）
・外部キー制約

→ ブロンズでは不要

【ブロンズ向けER図（シンプル）】
・「どんなデータがあるか」をリストアップ
・「どのデータとどのデータが繋がるか」を線で結ぶ
・ツールはシンプルに（紙、draw.io、Miro、Googleスライド等）

→ 厳密さより「整理する習慣」が目的
```

### カリキュラムへの組み込み案

```
【ブロンズ 第1部：データ整理の基礎】（新規追加 or 第2部の前段）

1. 現状のExcel業務を棚卸し
   ・どんなファイルがあるか
   ・どんな列（項目）があるか
   ・ファイル間の関係は
   ・すでに図がある場合はそれを活用

2. 簡易ER図を描く
   ・エンティティ（データの種類）を四角で描く

   ・エンティティ → テーブル
   ・属性 → カラム

```

## Django + Supabase 設計の一貫性

### 統一アーキテクチャ

```
【原則】
「Supabaseは便利なインフラ、頭脳はDjango」

・すべてのクライアントはDjangoを経由してデータにアクセスする
・Supabaseに直接アクセスしない
・この原則はシルバーからダイヤモンドまで一貫して変わらない
```

### 役割分担

```
【Django の役割】
├─ アプリケーションロジック（ビジネスルール）
├─ ORM（モデル定義、マイグレーション）
├─ ビュー・テンプレート（HTMX）
├─ REST API（モバイル向け、DRF）
├─ 管理画面（Django Admin）
└─ 認証・認可（django.auth）

【Supabase の役割】
├─ PostgreSQLホスティング（本番DB）
├─ ファイルストレージ（画像、添付ファイル）
└─ バックアップ・スケーリング

【Supabaseの使わない機能】
├─ Supabase Auth → Django認証に統一
├─ PostgREST API → Django経由でアクセス
├─ Edge Functions → Djangoで処理
└─ Realtime → 必要時はDjango Channels
```

### 重複機能でDjango側を選ぶ理由

#### 認証（Django Auth vs Supabase Auth）

```
【機能比較】
Django Auth    ：セッション認証、権限管理、ユーザーモデル拡張
Supabase Auth ：JWT認証、OAuth連携、マジックリンク

【Django を選ぶ理由】

＜開発面＞
・ビジネスロジックと認証が同じコードベース
・「この人はこのデータを見られるか？」の判定がPythonで書ける
・AIがロジック全体を理解しやすい
・テストが書きやすい（pytest + Django test client）

＜運用面＞
・ユーザー管理がDjango Adminで完結
・「このユーザーの権限を変更」がGUIでできる
・監査ログもDjango側で一元管理
・障害時の調査ポイントが1箇所

＜管理面＞
・認証の仕組みを理解するのはDjangoだけでよい
・Supabase Authの仕様変更に影響されない
・チーム内で「認証はDjango」と統一できる
```

#### データアクセス（Django ORM vs PostgREST）

```
【機能比較】
Django ORM  ：Pythonでクエリ、マイグレーション管理
PostgREST   ：URLパラメータでクエリ、自動API生成

【Django ORM を選ぶ理由】

＜開発面＞
・複雑なビジネスロジックをPythonで表現できる
・マイグレーションでスキーマ変更を履歴管理
・N+1問題等のパフォーマンス最適化がしやすい
・AIがPythonコードとして理解・修正できる

＜運用面＞
・Django Admin でデータ確認・修正が可能
・本番データの緊急修正もAdminから安全に実行
・「誰がいつ何を変更したか」をDjango側で記録可能

＜管理面＞
・スキーマ定義がmodels.pyに集約（Single Source of Truth）
・git管理でスキーマ変更の履歴が追える
・コードレビューでデータ設計をチェックできる
```

#### ファイルストレージ（Django経由 vs Supabase Storage直接）

```
【機能比較】
Django経由      ：FileField、アップロード処理をViewで制御
Supabase Storage：直接アップロード、CDN配信

【Django経由を選ぶ理由】

＜開発面＞
・アップロード時のバリデーション（サイズ、形式）がPythonで書ける
・「この人はこのファイルをアップロードできるか？」の権限チェック
・ファイルとデータベースの整合性を保証

＜運用面＞
・ファイル一覧がDjango Admin経由で確認可能
・不正ファイルの削除もAdmin経由で管理
・アクセスログがDjango側に集約

＜管理面＞
・「ファイルはSupabase Storage」「制御はDjango」と責務が明確
・Supabase Storageは「置き場所」として割り切る
```

#### API（Django REST Framework vs PostgREST）

```
【機能比較】
Django REST Framework：Pythonで柔軟にAPI設計
PostgREST           ：テーブル構造から自動生成

【Django REST Framework を選ぶ理由】

＜開発面＞
・ビジネスロジックを含むAPIが書ける
・レスポンス形式を自由にカスタマイズ
・認証・権限チェックとの統合が自然
・Swagger/OpenAPI ドキュメント自動生成

＜運用面＞
・APIのログがDjango側に集約
・レート制限等もDjango側で制御
・障害時のデバッグが容易（スタックトレース）

＜管理面＞
・APIの仕様がコードとして明示される
・PostgRESTの「テーブル構造＝API」は危険
  （内部テーブル構造の変更がAPIに直結）
```

### 運用・管理面でのDjango集約のメリット

```
【運用面：Django Admin で一元管理】
┌─────────────────────────────────────────┐
│ ・ユーザー管理                           │
│ ・データ確認・修正                       │
│ ・ファイル管理                           │
│ ・ログ確認                               │
└─────────────────────────────────────────┘
→ 複数の管理画面を行き来する必要がない

【監視・障害対応：監視ポイントがDjangoに集約】
┌─────────────────────────────────────────┐
│ ・エラーログ → Django                   │
│ ・アクセスログ → Django                 │
│ ・パフォーマンス → Django               │
│ ・Supabaseは「DBが動いているか」だけ    │
└─────────────────────────────────────────┘
→ 障害調査の入口が1つ

【管理面：学習・引継ぎコストの削減】
┌─────────────────────────────────────────┐
│ ・「ロジックはDjangoを見ればわかる」     │
│ ・Supabase固有機能の学習が不要           │
│ ・ドキュメントもDjango中心で済む        │
│ ・担当者交代時の引継ぎが容易             │
└─────────────────────────────────────────┘
→ 中小企業の限られたリソースに適合

【セキュリティ：アクセス制御がDjangoで完結】
┌─────────────────────────────────────────┐
│ ・Supabaseの公開設定ミスのリスクを排除   │
│ ・RLS（Row Level Security）設定不要     │
│ ・権限ロジックがPythonで明示的          │
└─────────────────────────────────────────┘
→ 「Supabaseは内部ネットワーク扱い」
```

### まとめ：なぜDjangoを選ぶのか

```
【Django を選ぶ理由】
・開発：AIと相性が良い、テストしやすい
・運用：Admin で一元管理、障害調査が容易
・管理：学習コスト削減、引継ぎが容易

【Supabase の役割】
・「PostgreSQL をホスティングしてくれるサービス」
・「ファイルを置く場所」
・頭脳は持たせない
```

### 設計の「誘惑」と対策

```
【誘惑の正体】
React NativeやFlutterには「Supabase公式SDK」がある。
SDKを使えばDjangoを通さずにSupabaseの機能を直接呼べる。
これは作り手の「手間を省きたい」という誘惑であり、
アプリのパフォーマンスの問題ではない。

【具体的な誘惑】

誘惑①：認証
  Django経由 → 自前でログインAPI作成、トークン管理
  Supabase直接 → supabase.auth.signIn() で3行で完了
  「Djangoで認証API書くの面倒…」

誘惑②：ファイルアップロード
  Django経由 → モバイル → Django API → Supabase Storage
  Supabase直接 → supabase.storage.upload() で直接アップロード
  「なぜわざわざDjangoを経由するのか…」

誘惑③：リアルタイム通知
  Django経由 → Django Channels等のWebSocket実装が必要
  Supabase直接 → supabase.from('table').on('INSERT', callback)
  「数行でリアルタイム機能が使えるのに…」

誘惑④：単純なCRUD
  Django経由 → View, Serializer, URL設定…
  Supabase直接 → supabase.from('shohin').select('*')
  「ただの一覧取得にDjangoのコード書く必要ある？…」

【なぜ誘惑に負けてはいけないか】
・ロジックがDjangoとモバイルアプリに分散する
・「この処理はどこにある？」が分からなくなる
・Webとモバイルで同じ処理を二重実装することになる
・テストが困難になる
・AIにコードを読ませても全体像が掴めなくなる

【パフォーマンスは理由にならない】
・Django経由は1ホップ増えるが、ミリ秒単位の差
・中小企業の業務アプリでは体感差ゼロ
・パフォーマンスが問題になるのは数万人同時アクセス等
・「手間」対「設計の一貫性」のトレードオフ
・一貫性を守る方が長期的な保守コストは下がる

【カリキュラムでの対策】
・プラチナでモバイル対応を教える際、最初にこの「誘惑」を説明する
・「なぜDjango経由にするのか」の理由を理解させる
・設計原則（関心の分離）との接続を示す
```

### PWA / Capacitor が推奨される理由

```
【モバイル対応の推奨順】
第1選択：PWA           → 役割維持、追加学習最小
第2選択：Capacitor     → 役割維持、WebViewラップ
第3選択：Flutter       → 役割維持可能だが誘惑あり
第4選択：React Native  → 役割維持可能だが誘惑あり

【PWA / Capacitorの優位性】
・HTMLをDjangoから受け取る構造のため、
  Supabaseに直接アクセスする手段がそもそもない
・「誘惑」自体が発生しない
・学習コストが最小
```
