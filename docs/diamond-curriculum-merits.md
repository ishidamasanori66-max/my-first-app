# ダイヤモンドカリキュラム：技術選定とメリット総括

## 概要

本ドキュメントは、中小企業向けAI伴走型開発教育「ダイヤモンドカリキュラム」における技術選定の根拠と、各視点からのメリットをまとめたものです。

---

## 設計思想

```
【コンセプト】
「データが次の一手を教えてくれる」
〜 蓄積したデータから、新しい事業価値を創出する 〜

・需要予測で廃棄ロス・機会損失を削減
・顧客分析でマーケティング精度を向上
・画像認識で検査・作業を自動化
・データドリブンな意思決定を全社に浸透
```

---

## 5ステージの一貫したストーリー

| ステージ | コンセプト | 改善対象 |
|---|---|---|
| ブロンズ | 「あなたの3時間を5分に」 | 個人の業務 |
| シルバー | 「Excelを送る業務をなくす」 | 組織の業務プロセス |
| ゴールド | 「二重入力をゼロに」 | 社内システム全体 |
| プラチナ | 「お客様がまた来たくなる仕組みを」 | 顧客接点・顧客体験 |
| **ダイヤモンド** | **「データが次の一手を教えてくれる」** | **事業価値の創出** |

```
【内から外へ、そしてデータから未来へ】
Bronze  → 自分の業務を効率化
Silver  → 社内の情報共有をデジタル化
Gold    → 社内システム同士を繋ぐ
Platinum → 顧客との接点を作る・強化する
Diamond → 蓄積データから次の一手を見つける
```

```
【DXステージとの対応】
Bronze〜Gold   = デジタイゼーション / デジタライゼーション
                 （既存業務の効率化・デジタル化）
Platinum       = 顧客体験の変革
Diamond        = デジタルトランスフォーメーション（本来のDX）
                 （データに基づく新しい価値の創出）
```

## プラチナからダイヤモンドへ

### プラチナ修了時点の状況

```
【蓄積されたデータ資産】
・売上データ（日別・商品別・店舗別）
・在庫データ（入出庫履歴）
・勤怠データ（出退勤パターン）
・顧客データ（購買履歴、来店頻度、属性）
・決済データ（金額、時間帯、支払い方法）
・通知データ（開封率、クリック率）
・クーポンデータ（利用率、効果測定）
・問い合わせデータ（内容、対応時間）

【残っている課題】
・データはあるが「分析」ができていない
・過去は見えるが「未来」が予測できない
・施策の効果を「定量的に」評価できない
・業種特有の課題を「データで」解決したい

→ これがダイヤモンドで解決する
```

### ダイヤモンドで実現すること

```
【Before（プラチナまで）】
・過去のデータをダッシュボードで見る
・人間が判断して次の手を打つ
・勘と経験に頼る部分が残る

【After（ダイヤモンド）】
・データが「明日」を予測する
・AIが「次の一手」を提案する
・施策の効果をデータで検証する
・業種特有の課題をデータサイエンスで解決する
```

## 共通基盤

### 第1部：データ分析基盤（8〜10時間）

```
・Supabaseからの分析用データ抽出
  → ブロンズで習得したSQL + pandasを活用
  → 分析用のデータセット作成
・探索的データ分析（EDA）
  → データの分布、相関、傾向の把握
  → 欠損値・外れ値の処理
・データ可視化（分析向け）
  → matplotlib / seaborn（ブロンズの発展）
  → Streamlit で分析ダッシュボード構築
・Google Colab / Jupyter の活用
  → ブロンズの環境を再活用
  → 試行錯誤しやすい環境

目標: 自社データを分析可能な形に整え、傾向を把握できる
```

### 第2部：機械学習の基礎（10〜14時間）

```
・機械学習とは何か
  → 「過去のパターンから未来を予測する」
  → 教師あり学習、教師なし学習の概念
・scikit-learn の基礎
  → 分類（この顧客は離反するか？）
  → 回帰（来月の売上はいくらか？）
  → クラスタリング（顧客をグループ分けする）
・モデルの評価と改善
  → 精度の測り方（正解率、適合率、再現率）
  → 過学習の防止（訓練データ vs テストデータ）
  → AIを活用したハイパーパラメータ調整
・実践：自社データで予測モデルを作る
  → 例：「次月の売上を予測する」

目標: 基本的な機械学習モデルを自社データで構築できる
```

### 第3部：予測モデルの構築（8〜12時間）

```
・時系列予測（Prophet）
  → 季節性、トレンド、イベント効果の分解
  → 需要予測、売上予測への適用
・顧客分析（RFM分析 + ML）
  → Recency（最終来店日）
  → Frequency（来店頻度）
  → Monetary（利用金額）
  → 機械学習で離反確率を予測
・AIとの連携
  → Claude APIで分析結果の解釈・レポート生成
  → 「この分析結果をもとに提案を作成して」
・Streamlitで分析ダッシュボード
  → 予測結果を見える化
  → 非エンジニアでも使えるUI

目標: 予測モデルを構築し、ビジネスに活かせるダッシュボードを作る
```

## 業種別テーマ（12〜20時間）

### テーマA：飲食店 ─ 需要予測とメニュー最適化

```
【解決する課題】
・食材の発注量が読めない → 廃棄ロス or 品切れ
・どのメニューが利益に貢献しているか不明
・天候・曜日・イベントの影響が読めない

【データ活用例】

1. 日別来客数予測
   ・過去の来客数 + 曜日 + 天候 + 近隣イベント
   → Prophet で翌日〜翌週の来客数を予測
   → 食材発注量を自動提案

2. メニュー分析（ABC分析 + 利益貢献）
   ・各メニューの売上、原価率、注文頻度
   → 利益貢献度の高い「推しメニュー」を特定
   → 赤字メニューの改善 or 廃止判断

3. 客単価の最適化
   ・セットメニューの組み合わせ分析
   → 一緒に注文されやすい組み合わせを発見
   → セット提案で客単価向上

【技術】
・Prophet（来客数の時系列予測）
・scikit-learn（メニュー分類、クラスタリング）
・pandas（ABC分析、クロス集計）
・Streamlit（店長向けダッシュボード）

【効果例】
・食品廃棄 30%削減（月5万円の原価削減）
・メニュー改定で利益率 5%向上
```

### テーマB：小売・アパレル ─ 在庫最適化とレコメンド

```
【解決する課題】
・在庫の過不足（売れ筋の欠品、死に筋の山積み）
・全顧客に同じおすすめ → 精度が低い
・セール時期の判断が勘頼み

【データ活用例】

1. 需要予測と自動発注提案
   ・商品別の販売トレンド + 季節性
   → 適正在庫数を予測
   → 発注タイミングを自動提案

2. 顧客セグメント × パーソナライズ推薦
   ・RFM分析で顧客をグループ化
   ・各グループの購買傾向を分析
   → 協調フィルタリングでおすすめ提案
   → プラチナのクーポン配信と連携

3. 値下げ最適化
   ・在庫回転率と利益率の分析
   → 値下げタイミングと割引率の最適化
   → 値下げしなくても売れる商品を特定

【技術】
・Prophet（商品別の需要予測）
・scikit-learn（顧客クラスタリング、協調フィルタリング）
・pgvector（商品の類似度検索 → プラチナで習得済み）
・Streamlit（バイヤー向けダッシュボード）

【効果例】
・欠品率 40%削減
・在庫回転率 20%改善
・レコメンド精度向上で客単価 15%アップ
```

### テーマC：医療・歯科 ─ 来院予測とリコール最適化

```
【解決する課題】
・定期検診のリコール（再来院促進）が一律
・どの患者が来院しなくなるか分からない
・予約枠の空き状況が最適化されていない

【データ活用例】

1. 来院間隔の予測
   ・患者ごとの来院パターンを分析
   → 次回来院予測日を算出
   → 最適なタイミングでリマインド送信
   （プラチナの自動通知と連携）

2. 離反リスク予測
   ・来院間隔の変化、キャンセル率、年齢、治療内容
   → 離反リスクの高い患者を早期検知
   → 特別なフォローアップを実施

3. 予約枠の最適化
   ・時間帯別の来院傾向分析
   → 混雑・空き予測
   → 効率的な予約枠設定

【技術】
・scikit-learn（離反予測：ランダムフォレスト）
・Prophet（来院数の時系列予測）
・pandas（来院パターン分析）
・Streamlit（院長向けダッシュボード）

【効果例】
・リコール来院率 25%向上
・離反率 30%改善
・予約枠の稼働率 15%向上
```

### テーマD：美容・サービス ─ 離反予測と来店サイクル分析

```
【解決する課題】
・顧客の来店サイクルが把握できていない
・離反しそうな顧客を事前に察知できない
・新規 vs リピートのバランスが分からない

【データ活用例】

1. 顧客ライフサイクル分析
   ・初回来店 → リピート → 常連 → 離反の各段階を可視化
   → 各段階の顧客数と推移を把握
   → 「常連化率」をKPIとして管理

2. 次回来店予測
   ・過去の来店間隔 + 施術内容 + 季節
   → 顧客ごとの最適な来店タイミングを予測
   → プラチナの自動リマインドと連携

3. 離反予兆の検知
   ・来店間隔が伸びている顧客を自動検出
   → 離反リスクスコアを算出
   → スコアに応じた施策（クーポン、特別メニュー）

【技術】
・scikit-learn（離反予測、生存分析）
・pandas（コホート分析、来店サイクル分析）
・Claude API（顧客ごとの施術提案文の生成）
・Streamlit（オーナー向け顧客分析ダッシュボード）

【効果例】
・離反率 20%改善
・リピート間隔 10%短縮
・LTV（顧客生涯価値）15%向上
```

### テーマE：製造業 ─ 品質検査と予知保全

```
【解決する課題】
・外観検査が目視頼み → 見落とし、属人化
・設備の故障が突発的に発生
・品質データの活用ができていない

【データ活用例】

1. 画像認識による外観検査
   ・製品写真をAIが自動判定
   → 不良品の自動検出
   → 検査員の負担軽減と精度向上

2. 予知保全
   ・設備のセンサーデータ（温度、振動、電流）
   → 異常パターンの学習
   → 故障の予兆を事前検知
   → 計画的なメンテナンスに切り替え

3. 品質トレンド分析
   ・不良率の推移、ロットごとの傾向
   → 品質低下の原因を早期に特定
   → 工程改善にフィードバック

【技術】
・Google Cloud Vision API / AWS Rekognition（画像認識）
・scikit-learn（異常検知、分類）
・TensorFlow Lite（エッジでの推論 ※発展）
・pandas（品質データ分析）
・Streamlit（品質管理ダッシュボード）

【効果例】
・検査時間 80%削減
・不良品流出 90%減
・設備の計画外停止 50%削減
```

### テーマF：自動車整備 ─ 需要予測と部品在庫最適化

```
【解決する課題】
・車検・点検の需要が季節変動する
・部品の在庫管理が勘頼み
・作業時間の見積もりが属人的

【データ活用例】

1. 車検・点検の需要予測
   ・顧客の車両データ + 車検期限
   → 月別の入庫台数を予測
   → スタッフのシフト最適化

2. 部品の需要予測と自動発注
   ・整備履歴 + 車種 + 走行距離
   → 必要部品を事前予測
   → 在庫切れゼロ、過剰在庫の削減

3. 作業時間の予測
   ・過去の整備記録（車種、作業内容、メカニックの習熟度）
   → 作業時間を予測
   → 正確な見積もり、効率的な作業配分

【技術】
・Prophet（入庫台数の時系列予測）
・scikit-learn（部品需要予測、作業時間予測）
・pandas（整備履歴分析）
・Streamlit（工場長向けダッシュボード）

【効果例】
・部品在庫コスト 25%削減
・作業効率 15%向上
・見積もり精度向上で顧客満足度アップ
```

```
【ダイヤモンドで追加】
```

### 技術の追加マトリクス

| カテゴリ | 技術 | 役割 | 難易度 |
|---|---|---|---|
| **機械学習** | scikit-learn | 分類・回帰・クラスタリング | ○ 中程度 |
| **時系列予測** | Prophet | 需要予測・売上予測 | ○ 中程度 |
| **可視化** | seaborn | 統計的可視化 | ◎ 簡単 |
| **ダッシュボード** | Streamlit | 分析結果の共有 | ◎ 簡単 |
| **画像認識** | Cloud Vision API | 製品検査・分類 | ◎ 簡単（API） |

### なぜStreamlitか

```
【Reactとの使い分け】

React（シルバーで習得）:
・業務アプリ（CRUD操作、フォーム、ワークフロー）
・顧客向けアプリ（LINE、ネイティブ）
・日常的に使うツール

Streamlit（ダイヤモンドで追加）:
・分析ダッシュボード（グラフ、予測結果の表示）
・経営者・管理者向けのレポートツール
・Python だけで作れる（HTMLやCSSの知識不要）
・AIに「Streamlitで可視化して」と言うだけ

→ 目的が違うので共存する
→ ReactアプリからStreamlitダッシュボードにリンク
```

### Streamlitのコード例

```python
import streamlit as st
import pandas as pd
from prophet import Prophet

st.title('📊 売上予測ダッシュボード')

# Supabaseからデータ取得
df = load_sales_data()

# Prophet で予測
model = Prophet()
model.fit(df)
future = model.make_future_dataframe(periods=30)
forecast = model.predict(future)

# グラフ表示
st.subheader('来月の売上予測')
fig = model.plot(forecast)
st.pyplot(fig)

# 予測値の表示
st.subheader('日別予測')
st.dataframe(forecast[['ds', 'yhat', 'yhat_lower', 'yhat_upper']])
```

```
┌─────────────────────────────────────────────────┐
│  ダイヤモンドはブロンズと円環を成す             │
│                                                   │
│  ブロンズ: Python + pandas + SQL + Colab          │
│      ↓                                            │
│  シルバー〜プラチナ: React + Supabase + ...      │
│      ↓                                            │
│  ダイヤモンド: Python + pandas + SQL + Colab      │
│              + scikit-learn + Prophet              │
```

## 注意点・課題

### 1. データ量の問題

```
【課題】
・中小企業のデータ量は限られる
・機械学習は大量データが前提と思われがち

【対応】
・少量データでも使えるモデルを選ぶ
  → 決定木、ランダムフォレストは少量でも動く
  → ディープラーニングは基本的にAPI利用
・ドメイン知識（業界の常識）で補完
  → 「夏はかき氷が売れる」をモデルに組み込む
・Prophet は数十件のデータでも予測可能
```

### 2. 過学習のリスク

```
【課題】
・小さなデータで複雑なモデルを作ると「過学習」
  → 訓練データにだけ合ったモデル
  → 新しいデータで外れる

【対応】
・シンプルなモデルを優先（オッカムの剃刀）
・訓練データとテストデータを分ける
・交差検証を行う
・AIに「このモデルは過学習していないか？」と確認
```

### 3. 解釈可能性

```
【課題】
・「AIがこう言っている」だけでは経営者は動かない
・なぜそう予測したのかの説明が必要

【対応】
・説明可能なモデルを選ぶ（決定木、線形回帰）
・特徴量の重要度を可視化
・Claude API で「この予測結果を経営者向けに説明して」
```

### 4. ディープラーニングの位置づけ

```
【方針】
・ダイヤモンドでは基本的にAPIとして利用
  → 画像認識: Cloud Vision API
  → テキスト分析: Claude API
  → これらはすでにプラチナで習得済み

・自前でディープラーニングモデルを「学習」するのは
  中小企業には基本的に不要
  → データ量、計算資源、専門知識の壁
  → API + scikit-learn で大半の課題は解決できる

・ただし、製造業の独自検査など、
  業種特有の画像認識が必要な場合は
  ファインチューニング（追加学習）を検討
```
